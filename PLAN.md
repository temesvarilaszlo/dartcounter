# Dart Counter: Implementation Plan

A personal, mobile-first dart counter that runs as an installable PWA on Android Chrome. Vanilla JavaScript only, MVC architecture, with game logic fully separated from the UI. Finished games are persisted in IndexedDB so long-term statistics can be computed.

This document is the source of truth. If something is unclear or contradictory, or a game rule is ambiguous, **stop and ask the user instead of guessing** (section 14 records the decisions already confirmed with the user).

---

## 1. Hard requirements (from the user)

- Vanilla JS only (ES modules). No frameworks, no bundler, no build step, no runtime dependencies.
- MVC with a clean split: `model` (pure logic and persistence, no DOM) / `views` (DOM only, no rules) / `controllers` (glue).
- Mobile-first: every screen must fit the viewport without page scrolling during a game (other screens may scroll inside their content area, never the navbar or input panel). Easy to use one-handed.
- Dartboard colour scheme everywhere: black, white (cream), red, green.
- **Use the `frontend-design` skill whenever touching frontend code** (`src/views/**`, `src/styles/**`, `index.html`). If the skill is not available in the agent's environment, follow section 11 instead.
- Do not use the phone's native numeric keyboard or `<input type="number">`. All numeric input goes through the on-screen keypad component.
- Invalid dart scores are rejected with a visible error. Busts are not recorded: a score that would bust is simply invalid, and a player who throws no score enters `0`.
- A game is written to the database **only when it finishes**. The in-progress game is mirrored to `localStorage` so a sudden exit loses nothing; a deliberate exit wipes it.
- At least **90% test coverage for the model** (lines, branches, functions). No UI tests required.
- Game types must be easily extendable. Initially: X01 and Cricket.

### 2.6 Service worker (`sw.js`) and precache

- `scripts/gen-precache.mjs` walks `index.html`, `manifest.json`, `src/**`, `icons/**`, `assets/**` and writes `precache.js` containing `self.PRECACHE = { version: "<hash of all file contents>", files: [...] }`. `pnpm dev` runs it automatically and the deploy workflow (2.10) runs it in CI, so `precache.js` is never committed and can never go stale. This removes the "forgot to add a file to the cache list" failure.
- `sw.js` does `importScripts('./precache.js')` and:
  - **install:** open cache `dartcounter-<version>`, `addAll(files)`, `skipWaiting()`.
  - **activate:** delete caches with other names, `clients.claim()`.
  - **fetch (same-origin GET only):** network-first with a 3 second timeout, falling back to cache; every successful response is written to the cache. Network-first means stale code is never served while online, and the timeout keeps the app usable on weak pub signal.
- IndexedDB and localStorage data are never touched by the service worker.

## 3. Architecture (MVC)

**Model** (`src/model`): all rules, state derivation, statistics, validation, persistence. Pure functions and small classes. No DOM. Fully unit-tested.

**View** (`src/views`): receives plain view-model objects from controllers and renders DOM; emits user intents via callbacks. Contains no game rules, no persistence calls, no stats maths. Per-game-type visual parts (scoreboard, input panel, leg history table) live in `views/gameTypes/<type>.js`.

**Controller** (`src/controllers`): handles routes and user intents, calls the model, builds view models, instructs views to render. Controllers are the only layer that talks to both. They receive dependencies from `main.js` (dependency injection); they never `new` a repository themselves.

**Composition root** (`main.js`): creates the IndexedDB connection, repositories, `activeGameStore`, game type registry, router and controllers.

Data flow: `User tap -> View callback -> Controller -> GameSession (model) -> new state -> Controller builds view model -> View renders`.

## 4. Data model

### 4.1 Relationships and the relational-vs-JSON decision

| Relationship | Decision | Reason |
|---|---|---|
| Game <-> Player | **Many-to-many, relational.** Separate `players` store; games reference `playerIds` | A player appears in many games; all-time stats need stable identity; renames must not rewrite games |
| Game 1..n Leg | **Embedded** in the game document (`legs[]`) | Always read together, saved atomically at game end |
| Leg 1..n Turn | **Embedded** in the leg (`turns[]`) | Same; replay needs the whole ordered list |
| Sets | Not an entity; derived from the leg order and config | Avoids redundant state |

Derived values (remaining score, averages, sets/legs won, winner) are **computed by replaying the log**. A small denormalised `result` is stored on a finished game purely for fast list rendering; tests must assert it always equals the replayed result.

### 4.2 Records

All records carry `schemaVersion` (start at `1`). Timestamps are stored as ISO 8601 UTC strings; everything shown to the user (dates, date-range filters, export filename) uses the phone's **local** time and local day boundaries. Ids come from `crypto.randomUUID()` (injectable for tests).

```js
// players store
{ id, name, nameKey /* trimmed, lowercased */, createdAt, schemaVersion }

// games store (finished games only)
{
  id, schemaVersion,
  type: "x01" | "cricket",            // key into the game type registry
  startedAt, finishedAt,
  config: {
    playerIds: [id, id],              // ordered = throw order, index = seat
    startingPlayerIndex: 0,           // always written as 0 (list order is the throw order, see 5.2); kept for the rotation maths in 6.1
    sets: { enabled: false, format: { mode: "firstTo"|"bestOf", value: 3 }, legsToWinSet: 3 },
    legs: { format: { mode: "firstTo"|"bestOf", value: 3 } },   // used when sets disabled
    typeConfig: { /* game type specific, see below */ }
  },
  legs: [
    {
      index: 0,                       // global leg number, 0-based
      starterIndex: 0,
      winnerIndex: 1,
      turns: [ /* type specific, see below */ ]
    }
  ],
  result: { winnerId, setsWon: { [playerId]: n }, legsWon: { [playerId]: n } }
}
```

`typeConfig`:
- X01: `{ startScore: 501, inRule: "straight"|"double", outRule: "straight"|"double" }`
- Cricket: `{ variant: "regular"|"cutThroat" }`

Turn payloads:
- **X01:** `{ playerIndex, score, darts }`. `score` is the 3-dart total (0 if nothing scored). `darts` is 3 for every turn except the checkout turn, where it is 1-3 from the modal. No per-dart values.
- **Cricket:** `{ playerIndex, darts: [ { n: 15..20|25, m: 1|2|3 } | { miss: true } ] }`. A turn has up to 3 darts (fewer only if the leg is won mid-turn). Ending a turn early fills the rest with misses.

IndexedDB layout (DB `dartcounter`, version 1):
- `players`: keyPath `id`, unique index `nameKey`.
- `games`: keyPath `id`, indexes `finishedAt`, `type`, `playerIds` (multiEntry).
- Upgrades live in a `migrations` map keyed by target version inside `idb.js`.
- Filtering and aggregation happen in memory (data volume is tiny: a leg is a few hundred bytes).

### 4.3 In-progress game mirror (localStorage)

Key `dartcounter.activeGame.v1`:

```js
{ schemaVersion: 1, savedAt, type, startedAt, config, legs: [ ...same shape as above, last leg may be incomplete ],
  pendingTurn: null | { /* partial cricket turn */ },
  players: [ /* player records in seat order, incl. new ones not yet in the DB */ ] }
```

- Written after every committed turn, undo and dart (cricket).
- Cleared on deliberate exit, on game finish (after the DB write succeeds) and on "Discard" at the resume prompt.
- On launch, if present and parseable, the main menu shows a **Resume / Discard** modal. Corrupt data is discarded with a toast.
- While a mirror exists, the main menu also shows a persistent **Resume game** card (so dismissing the modal never loses the game). Starting a new game while a mirror exists asks for confirmation before discarding it.
- Also stored: `dartcounter.lastConfig.v1` (last used pre-game config per game type, **including the players and their order**, used to prefill the pre-game screen).

### 4.4 Players

- Names: trimmed, 1-20 characters, unique case-insensitively within a game.
- Entering a name that matches an existing player (by `nameKey`) reuses that player and keeps its stored casing. The picker offers existing players as tappable chips.
- Brand-new players get ids at game start but are **written to the DB together with the game, in one transaction, at finish**. Quitting a game never leaves orphan players.
- No player deletion or renaming UI in this version (out of scope).

## 5. Game type extensibility

### 5.1 Game type definition (registry entry)

Each game type is one module exporting an object with this shape. Adding a game type means adding a model module, a view module, and registering both.

```js
{
  id: "x01",
  label: "X01",
  description: "Count down to zero",
  inputMode: "numpad" | "dartPad",        // which input component the game view mounts

  // Pre-game: declarative schema the pre-game screen renders (type specific fields only;
  // common fields are added by the app)
  preGameSchema: [ { key, label, kind, options, default, visibleWhen, validate } ],
  validateConfig(config) -> { ok, errors },
  normalizeConfig(rawFormValues) -> typeConfig,
  describeConfig(config) -> "501 · Double out",      // used in history rows

  // Rules (pure)
  replay(config, legs, pendingTurn?) -> GameState,
  evaluateInput(state, rawInput) -> { valid, error?, checkout?: { minDarts } },
  applyTurn(config, legs, turn) -> legs,             // returns a new log, never mutates

  // Stats
  legStats(config, leg) -> object,
  gameStats(config, legs) -> { [playerIndex]: object },
  gameStatsRows: [ { key, label, format } ],         // rows of the Game detail table
  legStatsRows: [ { key, label, format } ],          // per-player numbers in a leg's accordion header
  legHistory(config, leg) -> rows[round][seat],      // score history of one leg (null once the leg is over)
  allTime: { highlights: [...], sections: [...], compute(games, playerId) -> object },
  filterFields: [ ... ]                              // type specific history filters
}
```

Views register a counterpart in `views/gameTypes/index.js`: `{ scoreboard, inputPanel, legHistoryTable }` per type id. The generic game screen asks the registry for these parts.

### 5.2 Common config fields (added by the app to every game type)

- Number of players (1..`MAX_PLAYERS`, currently 2; the constant must be the only place to change when raising it) and player names (picker component).
- **Player list order = throw order.** There is no separate "who starts" field: the first player in the list throws first (`startingPlayerIndex` is always 0). Rows are reordered with ↑/↓ buttons (no drag and drop). Rotation per leg and per set follows 6.1.
- Match format:
  - **Sets toggle.** When off: legs format = `firstTo` or `bestOf` plus a value.
  - When on: sets format (`firstTo`/`bestOf` plus value) and "legs to win a set" (a first-to count).
  - Best-of values must be odd (the picker only offers odd numbers). Derived: `legsToWin` / `setsToWin` = `value` for first-to, `(value + 1) / 2` for best-of.
- Match format values (first-to / best-of, legs to win a set) use a **stepper** (−/+; best-of steps through odd values only). The **custom X01 start score** is entered with the in-app keypad modal. Never the native numeric keyboard. Player names use the normal text keyboard, which is acceptable for text.

### 5.3 X01 specific config

- Start score: chips for 101, 201, 301, 401, **501 (default)**, 601, 701, 801, 901, plus "Custom" (2-1001, entered with the keypad).
- In rule: straight (default) or double.
- Out rule: straight or **double (default)**.
- Rule tables are data-driven so more rules (for example master-out) can be added later without touching the engine.

### 5.4 Cricket specific config

- Variant: regular (default) or cut-throat. No warning about 2-player equivalence.

## 6. Game rules (model)

### 6.1 Match progression (common)

- **Starter rotation (confirmed by the user):**
  - Without sets: leg `i` (0-based) is started by `(startingPlayerIndex + i) % players`.
  - With sets: the first starter of each set rotates per set, regardless of who started the last leg of the previous set. Set `s` (0-based) is opened by `(startingPlayerIndex + s) % players`. Within a set, the starter then rotates per leg: leg `j` (0-based within the set) is started by `(setStarter + j) % players`.
  - Example (2 players, A starts set 1): set 1 legs are started A, B, A, B...; set 2 is opened by B whoever started the last leg of set 1; set 3 is opened by A again.
  - The resolved starter is also stored on each leg as `starterIndex`; tests must assert the stored value equals the derived one.
- Without sets: first to `legsToWin` legs wins the game.
- With sets: a set is won by reaching `legsToWinSet` legs within the set; the game is won by reaching `setsToWin` sets. Leg counters reset to 0 for the next set.
- The state exposes `phase`: `"playing" | "legComplete" | "gameComplete"`, plus `setsWon`, `legsWonInCurrentSet`, `legsWonTotal`, `currentPlayerIndex`, `legIndex`.

### 6.2 X01

Per-turn validation of a typed score `s` for a player with remaining `r`:

1. Must be an integer 0-180.
2. Not one of the numbers impossible with 3 darts: 163, 166, 169, 172, 173, 175, 176, 178, 179.
3. **Straight out:** `s > r` is invalid; `s == r` finishes the leg.
4. **Double out:**
   - `s > r` is invalid.
   - `r - s == 1` is invalid (would leave 1).
   - `s == r` is valid only if `r` is a finishable total: 2-170 excluding 159, 162, 163, 165, 166, 168, 169. Compute this by brute-forcing all 1-3 dart sequences ending on a double (D1..D20, bull = 50); do not hand-maintain the table.
   - Any other `s < r - 1` is valid.
5. **Double in (exact, confirmed):** until a player is "in", `s = 0` is valid (still not in). A non-zero score is valid only if some 1-3 dart sequence whose **first dart is a double** (D1..D20, bull 50) sums to `s` (plus the out rules above when `s == r`); it puts the player in. Consequences: max 170 on the going-in turn; 1, 168 and 171-180 are invalid ("171 can't be scored starting on a double"). Reuse the checkout brute-force engine; do not hand-maintain tables. Once in, always in for the rest of the leg. Reset at each leg start.
6. A score equal to the remaining that is not a legal finish is **invalid, not a bust** (same as rule 4).

Error messages must be specific and human: "Max score is 180", "163 can't be scored with 3 darts", "Too high, only 40 left", "That leaves 1, impossible with double out", "Can't check out 169 with double out".

**Checkout darts modal:**
- Shown when a valid turn finishes the leg. Compute `minDarts` = smallest `k` in 1..3 for which some k-dart sequence sums to the score and satisfies the out rule (last dart a double for double-out; any dart for straight-out). If the player is not yet "in" under double-in, additionally require the first dart to be a double.
- If `minDarts == 3`, do **not** show the modal; record 3 darts. Otherwise show buttons for `minDarts..3`.
- Examples to unit-test: double-out 2->1, 40->1, 50->1, 3->2, 41->2, 100->2, 110->2, 99->3, 170->3, 159 not finishable. Straight-out: 60->1, 61->2, 180->3, 21->1.

**Darts accounting:** every non-checkout turn counts 3 darts (including `0` turns); the checkout turn counts the modal value.

### 6.3 Cricket

Confirmed rules:
- Numbers: 15, 16, 17, 18, 19, 20 and Bull.
- A number is **closed** for a player after 3 marks (single = 1, double = 2, triple = 3; bull single = 1, bull double = 2, no triple bull; bull is worth 25).
- Marks beyond the third score points (`marks beyond 3 x number value`) only for as long as at least one opponent has that number **open**.
- **Regular:** the points go to the thrower; highest points wins.
- **Cut-throat:** the points are added to every opponent who still has the number open; lowest points wins.
- Leg ends immediately (mid-turn) when a player has closed all seven numbers and their points are `>=` all opponents (regular) or `<=` all opponents (cut-throat). A tie on points counts as a win for the closing player (confirmed).
- Darts at numbers 1-14 are recorded as misses.

Input: a dedicated dart pad (numbers 20..15 and Bull, single/double/triple selector that resets to single after each dart, miss button). A turn ends automatically after 3 darts or on "Next player" (remaining darts recorded as misses). Undo steps back one dart, then one turn.

Scoreboard: marks per number shown with tally symbols (none, `/`, `X`, circled X for closed) plus points per player. Never rely on colour alone.

### 6.4 `GameSession` (model facade used by controllers)

```js
GameSession.create(config, registry)        // new game
GameSession.restore(snapshot, registry)     // from localStorage mirror
session.state                               // derived GameState (via type.replay)
session.evaluateInput(raw)                  // { valid, error?, checkout? }  (X01)
session.submitTurn(turn)                    // commits, returns new state
session.addDart(dart) / session.endTurn()   // cricket
session.undo()                              // see below
session.startNextLeg()                      // from phase "legComplete"
session.snapshot()                          // for localStorage mirror
session.finish() -> gameRecord              // only valid in phase "gameComplete"; builds result
```

**Undo semantics:** pops the last turn (cricket: last dart first, then the last turn). If the current leg has no turns and a previous leg exists, discard the empty leg and reopen the previous leg (so undo works from a freshly started leg and from the leg summary modal, including after the final leg until `finish()` is called). Because phase is derived from the log, popping the winning turn automatically returns the phase to `"playing"`.

## 7. Statistics definitions

**Pooled averages everywhere** (leg, game, all-time): `total points / total darts x 3`. Not the mean of leg averages.

### 7.1 X01 (per player)

- **3-dart avg:** total points scored / darts thrown x 3 (busts do not exist; `0` turns count 3 darts; checkout turn counts the modal darts).
- **First 9 avg:** the first three turns of each leg, pooled: points in those turns / darts in those turns x 3 (a leg won within 3 turns uses the real dart count).
- **Highest finish:** highest checkout score.
- **Highest score:** highest single turn score.
- **Best leg:** fewest darts in a won leg. **Worst leg:** most darts in a won leg.
- **Interval buckets** (counts of turns, including `0` turns and checkout turns): `180`, `160-179`, `140-159`, `120-139`, `100-119`, `80-99`, `60-79`, `40-59`, `20-39`, `0-19`.

### 7.2 Cricket (per player)

- **Marks per round (MPR):** total marks / darts thrown x 3 (pooled, like the X01 average; a leg won on the first dart of a turn does not count as a full round).
- **Darts thrown:** misses count; darts after a mid-turn leg win do not exist.
- **Total marks**, **total points**. Also legs won.

### 7.3 Where they appear

- Game detail "Details" tab: X01 rows are 3-dart avg, First 9 avg, Highest finish, Highest score, Best leg, Worst leg. Cricket rows are MPR, Total marks, Total points. Rows = stats, columns = players.
- Leg accordion header: 3-dart avg, first 9 avg, darts thrown (X01); MPR, marks, points (cricket).
- All-time (section 9.5).

### 7.4 Solo (1-player) games

Count toward averages, darts thrown, 180s, interval buckets, highest finish/score, best/worst leg, MPR, marks, points and **games played**. They do **not** count toward games won or any win rate.

## 8. Navigation and flows

Hash routes (work on any static host, and make the Android back button controllable):

| Route | Screen |
|---|---|
| `#/` | Main menu |
| `#/new/:typeId` | Pre-game menu |
| `#/game` | Active game screen |
| `#/games/:id` | Game detail (finished game) |
| `#/stats` and `#/stats?tab=history` | Statistics |

Flow:

```
Main menu -> pick type -> Pre-game -> Start -> Game screen
Game screen -> [leg won] -> Leg summary modal -> Next leg -> Game screen
                                               -> Undo -> Game screen (leg reopened)
Game screen -> [game won] -> Summary modal -> Finish -> (save to DB, clear mirror) -> Game detail
Game screen -> Exit -> warning modal -> confirm -> clear mirror -> Main menu
Stats -> History tab -> tap game -> Game detail
Game detail -> Rematch -> Pre-game prefilled with the same config, player order rotated by one
App launch with mirror present -> Resume / Discard modal on the main menu (+ persistent Resume card)
Pre-game -> Start while a mirror exists -> confirm "Discard the game in progress?" -> Game screen
```

- **Rematch rotation:** the player list is shifted by one so the next player throws first (`[A, B, C]` -> `[B, C, A]`); works for any number of players.

- **Bottom navbar:** two items, Menu and Stats. It is **hidden during a game**; the game screen has its own Exit button.
- **Android back button during a game** triggers the same exit warning (push a sentinel history entry on entering `#/game` and intercept `popstate`).
- Unknown routes redirect to `#/`.
- During a game: request a screen wake lock (re-acquire on `visibilitychange`), release on leave.
- On first run (or after the first saved game) call `navigator.storage.persist()`.

## 9. Screens

All screens: mobile-first, `100dvh` layout, safe-area insets respected, touch targets at least 48x48 CSS px, `touch-action: manipulation`, `user-select: none` on interactive chrome. Verify at 320x568, 360x640, 390x844 and 412x915.

### 9.1 Main menu
- Grid of cards generated from the registry (label, description, icon). Initially X01 and Cricket. Tapping goes to `#/new/:typeId`.
- Resume / Discard modal on launch when an in-progress game exists, plus a persistent "Resume game" card at the top of the menu while it exists (shows type, players, current score summary).

### 9.2 Pre-game menu
- Rendered from the common fields plus the type's `preGameSchema` (field kinds: segmented, chips with custom, stepper, toggle, player picker). `visibleWhen` drives dependent fields (sets toggle reveals sets format and legs-to-win-set).
- Player list in throw order with ↑/↓ buttons per row (hidden for a single player) and a "throws first" marker on the first row.
- Inline validation; "Start game" disabled until the config is valid. Prefilled from `lastConfig` (including players and order) or a rematch config (order rotated).

### 9.3 Game screen
Layout (top to bottom, fixed, no page scroll):
1. Header: Exit button, game label (for example "501 · DO"), match progress ("Sets 1-0 · Legs 2-1" when sets are on, otherwise "Legs 2-1"; first-to / best-of target shown).
2. Scoreboard: all players visible. The **active player's** current score is rendered at the largest size (fluid font size via `clamp`), highlighted with a ring and a text marker (not colour alone); other players are compact (name, remaining, sets/legs won). Under the active score: **darts thrown in this leg, 3-dart avg in this leg, last score**. Inactive players show the same three stats in a compact form.
3. Input panel (bottom):
   - X01: value display (a `div`, not an input) with an error line (`role="alert"`), then a 3x4 keypad: `1-9`, backspace, `0`, OK; an Undo button sits next to the display. Max 3 digits.
   - Cricket: dart pad (see 6.3) plus a row showing the darts of the current turn, Undo and Next player.
4. Validation runs when OK is pressed; the error stays visible until the next key press. Invalid input is never committed.
5. Checkout darts modal (6.2), Leg summary modal, Exit warning modal ("Progress won't be saved. Exit?").
6. **Leg summary modal:** shows who won the leg (and the set if a set was won), darts and 3-dart avg for the leg, and buttons **Undo** (reopen the leg) and **Next leg**. After the final leg the primary button is **Finish game**, which saves, clears the mirror and navigates to Game detail; Undo remains available until then.

### 9.4 Game detail screen
- Header: date, game type + config description, result (winner, sets/legs).
- Tabs:
  1. **Details:** table, rows = stats (7.3), columns = players.
  2. **Legs:** one accordion per leg. Header: leg (and set) number, winner, 3-dart avg, first 9 avg, darts thrown (per player). Body: score history table, one group of columns per player with `Remaining` and `Scored` (X01), rows by round. Horizontal scroll inside the table only if more than 2 players. Cricket body shows marks hit and points per round.
- Buttons: Back, Rematch (opens pre-game prefilled, player order rotated by one). No delete here (delete lives in the history list).

### 9.5 Statistics screen
Two tabs: **All-time stats** and **Game history**.

**All-time stats:**
- Controls: game type switch (X01 / Cricket) and a **player selector** (defaults to the player with most games).
- X01 highlighted at the top: **180s thrown, all-time avg, darts thrown, games played.**
- Then the interval buckets (7.1), highest finish, highest score, best leg and worst leg. Because leg length depends on the start score, show best/worst leg as a small list grouped by start score (only scores the player has played) (confirmed).
- Cricket: games played, games won, MPR, total marks, total points, darts thrown.
- Solo games are included per 7.4 (not in games won).
- Empty states for no data.

**Game history:**
- Compact list, newest first: date, type and config description, players with result ("Alice 3-1 Bob", winner marked with an icon and bold, not just colour), delete button per row.
- Tap a row opens Game detail. Delete opens a confirmation modal; on confirm remove from DB and refresh both tabs.
- **Filters** (bottom sheet with chips; active count badge on the filter button; clear all): game type, date range, players (multi), number of players, match format (sets on/off, first-to/best-of, values), plus each type's `filterFields` (X01: start score, in rule, out rule; cricket: variant).
- JSON **Export** and **Import** buttons live at the bottom of this screen (see 10).

### 9.6 Navbar
Fixed bottom, two items (Menu, Stats) with icon + label, active item marked by an underline and weight, not only colour.

## 10. Backup and storage safety

- **Export:** `{ app: "dartcounter", schemaVersion, exportedAt, players: [...], games: [...] }` downloaded as `dartcounter-YYYY-MM-DD.json` (local date) via Blob + anchor download.
- **Import:** file picker, validate structure and `schemaVersion`, show a confirm modal with counts, **merge** by id (skip existing games). If an imported player's `nameKey` matches an existing player with a different id, remap that player's id inside the imported games. Reject files from a newer schema version with a clear message.
- Call `navigator.storage.persist()` as in section 8.
- All import/export logic lives in `model/persistence/backup.js` and is unit-tested; only the file picker/download glue is in the view/controller.

## 11. Visual design brief (fallback if the `frontend-design` skill is unavailable)

When the skill is available it takes precedence for aesthetic decisions; the constraints below always apply.

Tokens (`styles/tokens.css`):

```css
:root {
  --board-black: #0b0b0c;
  --board-ink:   #17171a;   /* raised surfaces */
  --board-line:  #2a2a2f;
  --board-white: #f4efe1;   /* cream, like the single segments */
  --board-red:   #c1121f;
  --board-green: #0e7a3b;
}
```

- Dark base (black), cream-white text, **green = primary/confirm**, **red = destructive/error/undo**. Optional dartboard-inspired details: alternating black/cream segment strips, a concentric ring motif on the menu and icon.
- Contrast: all text/background pairs at least 4.5:1 (check white on red and white on green).
- Red/green must never be the only signal: pair with icons, text labels, outlines or weight (colour-blind users, outdoor glare).
- Typography: **Barlow Condensed Bold** (OFL, self-hosted woff2 in `assets/fonts/` with `OFL.txt` committed, single weight) for big numbers with `font-variant-numeric: tabular-nums`; system UI font for the rest. No requests to external font/CDN hosts at runtime (offline requirement).
- Large, clearly separated keypad keys with pressed-state feedback; honour `prefers-reduced-motion`.
- Modals trap focus, close on Escape/back where safe, and are labelled for screen readers.

## 12. Testing

- Location: `tests/` mirroring `src/model`. Runner: `node --test`. Assertions: `node:assert/strict`.
- Coverage gate: `pnpm test:coverage` (in the container) must pass with >= 90% lines, branches and functions over `src/model/**` (this **includes** the IndexedDB repositories, tested with `import "fake-indexeddb/auto"`).
- Platform dependencies are injected so the model is testable: id generator, clock, `localStorage`-like store, IDB factory.
- Required test areas:
  - **X01 rules:** full validation matrix (0-180 boundaries, the nine impossible numbers, straight vs double out, leaves-1, exact checkout table vs brute force, double-in behaviours including the exact going-in table: 1, 168, 171-180 invalid, 170 valid, 0 keeps the player out), `minDarts` examples from 6.2, darts accounting.
  - **Match progression:** best-of/first-to derivation, odd best-of enforcement, sets and legs counters, phase transitions, and starter rotation (no sets; with sets, including the case where the previous set's last leg was started by either player; 3-player rotation).
  - **Cricket:** mark accumulation, closing, scoring only while an opponent is open, cut-throat distribution, win condition (including tie), mid-turn leg end, 1-player and 3-player cases.
  - **Undo:** across turns, across leg boundaries, after final leg, cricket dart-level undo; replay determinism (state from log equals live state).
  - **Stats:** pooled averages vs mean of averages (use the 15-dart/30-dart example: pooled 66.8, not 75.15), first 9, buckets (every boundary), best/worst leg, highest finish, cricket MPR (marks / darts x 3, including a leg won mid-turn).
  - **statsService:** all-time aggregation per player and type, solo games (counted in played, not in won), best/worst leg grouped by start score, every filter (date range on local day boundaries), empty inputs.
  - **Pre-game helpers (model):** rematch rotation (2 and 3 players), `lastConfig` round-trip including player order.
  - **Persistence:** IDB repositories (CRUD, unique `nameKey`, atomic game + new players write, delete), migrations from a fixture, `activeGameStore` (write/read/clear/corrupt data), backup export/import (merge, id remap, bad file, newer schema).
  - **Registry:** registering and listing game types, duplicate id rejection.
- No UI tests required.

## 14. Resolved decisions (confirmed with the user, 2026-11-09)

1. **Tooling:** pnpm only; all Node commands in a self-contained dev container (2.9); nothing reused from shared/work repos.
2. **Hosting:** public GitHub repo, GitHub Pages via Actions (2.10, milestone 9); `precache.js` generated in CI and gitignored.
3. **Docs/commits:** `README.md` kept current; one commit per completed milestone on `main`.
4. **Double-in:** exact validation by brute force (first dart a double), not the "anything but 1" simplification (6.2 rule 5).
5. **Cricket tie:** the closing player wins on equal points (`>=` regular, `<=` cut-throat).
6. **Cricket "Next player":** fills the remaining darts with misses.
7. **Player order = throw order:** no "who starts" field; ↑/↓ reorder; `startingPlayerIndex` always 0 (5.2).
8. **Rematch:** opens pre-game prefilled with the player order rotated by one (8).
9. **Pre-game numeric input:** steppers for match-format values; keypad modal only for the custom X01 score.
10. **`lastConfig`** includes players and their order.
11. **In-progress game safety:** persistent Resume card on the menu; confirmation before a new game discards the mirror.
12. **Best/worst leg (all-time):** grouped by start score.
13. **Cricket MPR:** marks / darts x 3.
14. **Solo games:** counted in all stats and games played, not in games won (7.4).
15. **Display font:** Barlow Condensed Bold, self-hosted, OFL licence committed.
16. **Time:** stored in UTC; displayed, filtered and named (export file) in local time.
17. **Undo from a freshly started leg** (X01 and cricket) discards the empty leg and removes the previous leg's winning input in one tap (2026-11-09).
18. **Cricket undo is dart by dart:** once the pending turn is empty, undo reopens the previous turn minus its last dart, including misses filled in by "Next player" (2026-11-10).
19. **Cricket marks (MPR, total marks):** only marks that close a number or score points count; marks on a dead number do not (2026-11-10).

Anything not covered here or elsewhere in this plan: ask the user.

## 15. Out of scope (for now)

Player renaming/deletion, more than 2 players (architecture must allow it via `MAX_PLAYERS`), more game types, cloud sync, sound/haptics, localisation (UI is English; dates formatted with `Intl`), master-out, per-dart X01 input.
